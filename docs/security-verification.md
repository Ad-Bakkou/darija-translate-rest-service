# Security architecture and verification

## Authentication and authorization

The application uses Jakarta Security 3.0 with Open Liberty's `appSecurity-5.0` feature. Liberty integrates `HttpAuthenticationMechanism` through its Jakarta Authentication servlet bridge. `SecurityConfiguration` delegates Basic credential parsing to `BasicAuthenticationCredential` and validation to `IdentityStoreHandler` / `TranslatorIdentityStore`.

`TRANSLATOR_USERNAME` and `TRANSLATOR_PASSWORD` configure a single local development account. Missing, blank or invalid username configuration rejects all protected requests; no default account exists. Matching is exact and case-sensitive. Temporary comparison byte arrays are cleared, but configured credentials necessarily remain in the backend process environment/memory.

Valid credentials establish group `translators`; `server.xml` maps that group using `access-id="translators"` to role `translator`. The servlet descriptor protects `/*` for every HTTP method except the exact `/api/health` mapping. Invalid authentication returns HTTP 401 with a Basic challenge; an authenticated caller without the role receives 403. Authentication errors generated by the container are not guaranteed JSON. SSO is disabled; cookies do not replace request authentication.

## Liberty malformed-header compatibility handler

Open Liberty 25.0.0.10 can throw `NullPointerException` or `StringIndexOutOfBoundsException` in `WebProviderAuthenticatorProxy.authenticateForOtherMechanisms` while auditing certain malformed Basic headers. `SecurityErrorServlet` converts only these exception types with that exact first non-JDK stack frame to HTTP 401. Other exceptions remain HTTP 500. The handler establishes no identity, accepts no invalid credentials, and its URL remains protected.

The runtime may still generate internal FFDC for this container defect. Logs remain excluded from version control. After a future Liberty upgrade, rerun the malformed-header regression tests and reassess whether the handler is still required.

## Credential and transport boundaries

The Gemini key belongs only to the Java process and is supplied through its environment. Clients authenticate to the fixed local REST endpoint; they never receive or send the Gemini key. Basic authentication encodes credentials but does not encrypt them. The supported development route is loopback HTTP, with physical Android using USB ADB reverse. Remote deployment requires HTTPS and a separate access-policy review; no production HTTPS deployment is claimed.

Chrome keeps credentials in trusted extension session storage; Python uses process memory/environment; PHP reads its server environment; mobile uses SecureStore where available with a labeled session-memory fallback. Sufficiently privileged local processes and debuggers can access secrets in memory. Do not log credentials, Authorization values, user text or raw provider bodies. Backend diagnostic records contain only model/status/category/timing metadata.

## Repeatable verification

Run `mvn -B -f backend/pom.xml verify` from the repository root. Tests start an isolated Liberty runtime on an ephemeral loopback port, generate temporary accounts and inject a deterministic translation alternative only into a copied test WAR. The production WAR excludes that alternative. Ordinary tests do not call Gemini.

Coverage includes public health, wrong/missing/malformed credentials, challenge headers, valid authenticated JSON, validation failures, protected path/method variants, role denial, missing account configuration, restart behavior, cookie-only rejection and credential leakage checks. A call counter verifies that rejected authentication and invalid input do not invoke translation.

For a running, correctly configured local backend:

```powershell
pwsh -File docs/verify-security.ps1 -AnonymousOnly
# With translator credentials configured, also test authenticated invalid input:
pwsh -File docs/verify-security.ps1
# Explicit opt-in: one real provider translation
pwsh -File docs/verify-security.ps1 -Live
```

`-AnonymousOnly` checks public health and rejected requests without credentials. The default mode requires translator environment credentials and also tests authenticated invalid input. Use `-Live` only when intentionally checking the provider. See the [API reference](api-reference.md), [client setup](client-setup.md) and [testing summary](testing.md).
